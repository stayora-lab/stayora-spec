# F1. Spacing and layout foundation

## Small scale

Use one compact, monotonic spacing scale based on a base unit. Names such as `space.1` through `space.8` describe increasing rhythm; their exact reference values remain an implementation/design decision. Do not create one-off gaps for individual screens.

## Layout principles

- **Page shell:** establish a predictable outer gutter and a readable content measure. A full-bleed region is used only when the content purpose needs it.
- **Content width:** constrain reading and decision content; allow tables, calendars and evidence views to use the width their task needs rather than forcing a marketing column.
- **Sections:** use spacing and headings to express information hierarchy before borders or shadows.
- **Cards/panels:** group a coherent responsibility or evidence set. Avoid card grids that fragment one canonical object into competing truths.
- **Forms:** pair every input with a label, help/error relationship and an explicit action scope. Keep consequential summaries adjacent to the commit action.
- **Lists/tables:** optimize for repeated comparison, provenance and attention. Preserve object identity and avoid using density as a substitute for hierarchy.
- **Marketplace:** prioritize property/unit discovery, dates, price and bookability projection with calm whitespace.
- **Guest Stay Access:** prioritize current Stay/access information and field readability; mobile-first constraints are relevant.
- **Operational views:** allow higher density for Unit × Time, assignments, incidents and evidence while retaining scan paths and safe action boundaries.

Spacing does not encode domain state. Layout may surface attention or provenance but cannot turn a projection into canonical truth.
