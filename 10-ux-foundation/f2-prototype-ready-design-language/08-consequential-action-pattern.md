# F2. Consequential-action presentation pattern

This pattern translates E1's grammar into a proportional composition. It is not a 12-step wizard and does not create an approval process.

## Required information by consequence

| Information | Low-risk filter/navigation | Consequential mutation |
|---|---|---|
| Current truth | Optional context | Required summary, including stale/unknown/conflict posture. |
| Acting context | Only when it changes interpretation | Required when authority or relationship matters. |
| Resource scope | Optional | Required: Property/Unit × Time, Stay, Request or other canonical scope. |
| Action | Clear control label | Explicit verb and object. |
| Consequence | Usually omitted | Show known reversible/irreversible or downstream effect; do not invent policy. |
| Uncertainty | Surface if it affects navigation | Always surface material UNKNOWN, pending or conflict. |
| Revalidation | Implicit | Required before commitment; stale truth routes to safe recovery. |
| Outcome | Lightweight feedback | Persistent outcome with updated projection. |
| Provenance | Optional | Visible where source/evidence/actor changes the decision. |
| Handoff/attention | Optional | Show responsible next context when action cannot finish locally. |

## Example: Owner Block presentation

A composed `OwnerBlockConfirmation` may show Property/Unit × Time, current Inventory basis/conflicts, acting Working Context and authority basis, intended block, known consequence, revalidation result, final canonical outcome and provenance. It must not infer authority from an Owner label, hide conflict, decide precedence or choose a duration.

## Friction rule

Use confirmation, review or explicit acknowledgement when the action affects Inventory, money, an external Guest, delegation, or a hard-to-reverse truth. Keep low-risk filters and navigation immediate. Friction communicates consequence; it never substitutes for authority or policy.
